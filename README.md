# PaymentCore

Учебный банковский backend на C#: пользователи, счета, пополнение, переводы между счетами и выпуск дебетовых карт.

Проект посвящён надёжной работе с деньгами и платёжными данными: деньги не должны теряться, дублироваться или появляться из ниоткуда, а данные карты не должны храниться там, где им не место.

> Это учебный проект. Реальных карт, денег и подключения к банкам здесь нет.

## Стек

- C#, .NET 10, ASP.NET Core (контроллеры)
- Entity Framework Core + PostgreSQL
- Docker / Docker Compose
- xUnit (юнит-тесты и интеграционные тесты)
- Scalar (интерактивная документация API)

## Архитектура

Четыре слоя, зависимости направлены внутрь:

- `PaymentCore.Domain` — сущности и бизнес-правила (`User`, `Account`, `LedgerEntry`, `Card`, `DebitCard`), генерация и проверка номера карты. Не зависит от других слоёв.
- `PaymentCore.Application` — сервисы и сценарии (создание счёта, пополнение, перевод, выпуск карты). Работает с базой через интерфейс `IAppDbContext`.
- `PaymentCore.Infrastructure` — `AppDbContext`, EF Core, миграции, PostgreSQL.
- `PaymentCore.Api` — контроллеры, настройка DI, запуск приложения.

## Реализованный функционал

### Счета и переводы

- Создание пользователей и счетов.
- Пополнение счёта и получение текущего баланса.
- Переводы между счетами с проверкой валюты, существования счетов и достаточности средств.
- Защита от перевода на тот же счёт.
- Все денежные операции выполняются через методы доменной модели с проверками.

### Проводки (Ledger)

Каждое изменение баланса сопровождается записью `LedgerEntry`:

- Зачисление хранится как положительное значение.
- Списание хранится как отрицательное значение.
- Перевод создаёт две проводки: списание со счёта отправителя и зачисление на счёт получателя.

### Атомарность операций

Списание, зачисление и создание обеих проводок сохраняются одним `SaveChangesAsync`.

Для реляционной базы данных EF Core использует транзакцию при сохранении изменений одним вызовом `SaveChangesAsync`. Это обеспечивает принцип «всё или ничего»: если сохранение не удалось, изменения откатываются.

### Конкурентность

Реализован механизм оптимистической конкурентности для счетов:

- У счёта есть поле `Version`.
- При изменении баланса версия увеличивается.
- EF Core использует версию как токен конкурентности при обновлении записи.
- Если другой запрос успел изменить счёт, сохранение со старой версией вызывает `DbUpdateConcurrencyException`.
- API возвращает `409 Conflict`.

Механизм проверен:
- Вручную — параллельными HTTP-запросами к API: один перевод выполняется успешно, второй получает конфликт версий.
- Автоматически — интеграционным тестом с PostgreSQL и двумя независимыми `DbContext`, проверяющим конфликт при сохранении устаревших данных.

### Карты

- Выпуск дебетовых карт, привязанных к счетам.
- Абстрактный класс `Card` и наследник `DebitCard`.
- Генерация номера по алгоритму Луна.
- Условный BIN `400000`.
- Использование криптостойкого `RandomNumberGenerator` для генерации случайных цифр.
- Блокировка и разблокировка карт.
- Обработка просроченных карт: просроченную карту можно заблокировать, но нельзя разблокировать с возвращением в активное состояние.

### Защита платёжных данных

- Полный номер карты не хранится в базе данных — сохраняются только последние четыре цифры.
- CVV не хранится вообще.
- Полный номер карты и CVV возвращаются клиенту только один раз при выпуске карты.
- Баланс хранится на счёте, а карта привязана к нему через `AccountId`.

> Такой подход соответствует принципу минимизации хранения платёжных данных. В частности, CVV нельзя хранить после авторизации в соответствии с PCI DSS.

### Типы данных и бизнес-правила

- Денежные значения хранятся в `decimal` (`numeric` в PostgreSQL).
- Идентификаторы — `Guid` (`uuid`).
- У свойств сущностей используются закрытые сеттеры (`private set`), а изменение состояния выполняется через методы доменной модели.
- Ошибки бизнес-логики обрабатываются middleware и возвращаются с соответствующими HTTP-статусами.

## Запуск

Требуются .NET 10 SDK и Docker.

```bash
# 1. Запустить базу данных
docker compose up -d

# 2. Применить миграции
dotnet ef database update \
  --project src/PaymentCore.Infrastructure \
  --startup-project src/PaymentCore.Api

# 3. Запустить API
dotnet run --project src/PaymentCore.Api
```

Интерактивная документация API:

[http://localhost:5266/scalar/v1](http://localhost:5266/scalar/v1)

> Пароль к базе в `docker-compose.yml` и `appsettings.json` учебный и предназначен только для локальной разработки.

## Эндпоинты

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | `/users` | Создать пользователя |
| POST | `/accounts` | Создать счёт |
| POST | `/accounts/{id}/deposit` | Пополнить счёт |
| GET | `/accounts/{id}` | Получить баланс счёта |
| POST | `/transfers` | Перевести деньги между счетами |
| POST | `/accounts/{accountId}/cards` | Выпустить дебетовую карту |

## Тесты

Запуск всех тестов:

```bash
dotnet test
```

Покрытые сценарии:

- Пополнение и списание средств со счёта.
- Защита от отрицательного баланса.
- Корректное увеличение версии счёта при изменении баланса.
- Отсутствие изменения версии при неудачной операции.
- Блокировка и разблокировка карты.
- Обработка просроченных карт.
- Проверка алгоритма Луна: корректный номер, опечатка, неверная длина и недопустимые символы.
- Генерация номеров карт: 1000 сгенерированных номеров проходят проверку, имеют длину 16 цифр и BIN `400000`.
- Генерация CVV.
- Успешные и неуспешные переводы между счетами.
- Проверка балансов и записей Ledger после переводов.
- Интеграционные тесты с PostgreSQL.
- Проверка оптимистической конкурентности: конфликт при попытке сохранить изменения с устаревшей версией счёта.

## Планы развития

- История проводок с категориями и статистика расходов (графики).
- Упрощённые кредитные карты: лимит, задолженность, проценты и льготный период.
- Идемпотентность переводов для защиты от повторной обработки одного запроса.
- JWT-авторизация: регистрация, вход и защита эндпоинтов.
- Полноценный автоматический интеграционный тест с синхронным запуском конкурирующих переводов.
