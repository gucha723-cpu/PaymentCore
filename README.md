# PaymentCore

Учебный банковский backend на C#: пользователи, счета, пополнение, переводы между счетами и выпуск дебетовых карт. Проект про то, как надёжно работать с деньгами и платёжными данными: деньги не должны теряться, дублироваться или появляться из ниоткуда, а данные карты не должны храниться там, где им не место.

> Это учебный проект. Реальных карт, денег и подключения к банкам здесь нет.

## Стек

- C#, .NET 10, ASP.NET Core (контроллеры)
- Entity Framework Core + PostgreSQL
- Docker / Docker Compose
- xUnit (юнит-тесты)
- Scalar (интерактивная документация API)

## Архитектура

Четыре слоя, зависимости направлены внутрь:

- `PaymentCore.Domain` - сущности и бизнес-правила (`User`, `Account`, `LedgerEntry`, `Card`, `DebitCard`), генерация и проверка номера карты. Ни от чего не зависит.
- `PaymentCore.Application` - сервисы и сценарии (создать счёт, пополнить, перевести, выпустить карту). Работает с базой через интерфейс `IAppDbContext`.
- `PaymentCore.Infrastructure` - `AppDbContext`, EF Core, миграции, PostgreSQL.
- `PaymentCore.Api` - контроллеры, настройка DI, запуск приложения.

## Ключевые идеи

- **Проводки (ledger).** Каждое изменение баланса записывается как `LedgerEntry`. Зачисление хранится как положительное число, списание как отрицательное. Сумма всех проводок равна сумме балансов.
- **Атомарный перевод.** Списание, зачисление и обе проводки сохраняются одним `SaveChangesAsync`, то есть в одной транзакции: записывается всё или ничего.
- **Типы данных.** Деньги хранятся в `decimal` (`numeric` в PostgreSQL), идентификаторы в `Guid` (`uuid`): без ошибок округления и угадываемых id.
- **Защищённые сущности.** У свойств `private set`, изменения идут только через методы (`Deposit`, `Withdraw`) с проверками.
- **Понятные ошибки.** Перевод на тот же счёт, несуществующий счёт и нехватка средств возвращают 400/404 с текстом, а не 500.

### Карты

- **Номер по алгоритму Луна.** Номер из 16 цифр с условным BIN `400000`. Последняя цифра подбирается так, чтобы номер проходил проверку Луна. Случайные цифры берутся из криптостойкого `RandomNumberGenerator`.
- **Полный номер не хранится.** В базе лежат только последние 4 цифры, срок действия и статус. Полный номер и CVV возвращаются клиенту один раз, в ответе на выпуск карты, и восстановить их потом нельзя.
- **CVV не хранится вообще.** Это соответствует требованию PCI DSS не хранить CVV после авторизации.
- **У карты нет своих денег.** Баланс живёт на счёте, карта привязана к нему через `AccountId`.
- **Наследование.** `Card` абстрактный, `DebitCard` его наследник. EF Core хранит иерархию в одной таблице `Cards` с колонкой-дискриминатором (TPH).

## Запуск

Нужны .NET 10 SDK и Docker.

```bash
# 1. База данных
docker compose up -d

# 2. Таблицы (миграции)
dotnet ef database update --project src/PaymentCore.Infrastructure --startup-project src/PaymentCore.Api

# 3. API
dotnet run --project src/PaymentCore.Api
```

Документация и тестовые запросы: http://localhost:5266/scalar/v1

> Пароль к базе в `docker-compose.yml` и `appsettings.json` учебный, только для локальной разработки.

## Эндпоинты

- `POST /users` - создать пользователя
- `POST /accounts` - создать счёт
- `POST /accounts/{id}/deposit` - пополнить счёт
- `GET /accounts/{id}` - баланс счёта
- `POST /transfers` - перевод между счетами
- `POST /accounts/{accountId}/cards` - выпустить дебетовую карту (полный номер и CVV возвращаются один раз)

## Тесты

```bash
dotnet test
```

Покрыто:

- доменная логика `Account` (пополнение, списание, защита от ухода в минус);
- алгоритм Луна: корректный номер, номер с опечаткой, неверная длина, буквы в номере;
- генерация номера (1000 генераций проходят проверку, длина 16, BIN `400000`) и генерация CVV.

## Планы

- Блокировка карты
- История проводок с категориями и статистика трат (графики)
- Упрощённые кредитные карты (лимит, долг, проценты, льготный период)
- Защита от одновременных переводов (конкурентность) и идемпотентность
- JWT-авторизация
- Тесты на сервисы и интеграционные тесты
